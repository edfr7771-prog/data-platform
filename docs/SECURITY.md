# ملاحظات الأمن (Phase 1)

## المنفَّذ ومُختبَر
- مصادقة بلا كلمات مرور؛ رموز HMAC؛ حدود إرسال ومحاولات ذرية تحت التزامن؛ استهلاك ذري؛ إعادة تحقق عند الاستهلاك.
- جلسات: SHA-256 فقط في القاعدة، HttpOnly + SameSite=Lax (+Secure على https)، جلسة جديدة عند الدخول، إبطال عند الخروج.
- CSRF: `Sec-Fetch-Site` ثم `Origin` ثم `Referer`.
- تفويض خلفي بثلاثة حراس + اختبار بنيوي يمنع تجاوزها. حساب ناقص محجوب عن كل API محمي.
- عزل المؤسسات: `org_id` من الجلسة في كل استعلام؛ اختُبر هجوم مؤسسة على أخرى عبر API مباشرة (قراءة/تعديل/حذف/تصدير/استيراد/تدقيق).
- التدقيق داخل معاملة العملية: لا عملية حساسة بلا أثر.
- ملفات الاستيراد: امتداد وحجم ومحتوى ثنائي وترميز وحد صفوف، وتنقية اسم الملف؛ تحصين التصدير من حقن الصيغ.
- رؤوس أمان: `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`, `HSTS`؛ بلا `X-Powered-By`.
- خطوط مستضافة ذاتيًا: لا طلب لطرف ثالث يكشف عنوان الزائد.
- أسرار من البيئة فقط؛ `.env.example` بلا أسرار؛ لا نطاق ثابت في الكود (APP_URL).
- عنوان IP يُخزَّن مجزّأ بـHMAC لا خامًا.

## اختُبرت حساسية الفحوص
كُسر الكود عمدًا في ثماني نقاط (عزل القراءة والحذف، الصلاحيات، أقفال التزامن، بوابة الاكتمال، حقن الصيغ، إعادة تحقق التسجيل، إعادة تحقق الدخول، CSRF) فأعطى الاختبار التكاملي 18 إخفاقًا مقابلة، ثم عاد كاملًا بعد استعادة الكود (103 فحصًا يومها، و109 الآن بعد إضافة فحوص CSRF).

## قيود معروفة (لم تُعالَج بعد)
- محدّد المعدل العام داخل الذاكرة (لكل نسخة تشغيل): يلزم مخزن مشترك عند تعدد النسخ. حدود الرموز في القاعدة وسليمة.
- لا رأس `Content-Security-Policy` بعد (يحتاج ضبطًا مع سكربتات Next المضمّنة).
- لا مهمة دورية لحذف رموز التحقق المنتهية (الاحتفاظ بها يزيد مع الوقت).
- قفل «15 محاولة فاشلة/ساعة» يوقف طلب رموز جديدة للمعرّف (يمكن استغلاله لتعطيل معرّف بعينه ساعة).
- مساري SMTP وSMS لم يُختبرا أمام مزوّد حقيقي.
- لا تصدير ولا حذف لبيانات الحساب بعد.
- مؤسسة واحدة نشطة لكل مستخدم؛ ولا دعوة أعضاء (الأدوار تُسند من القاعدة).
- **هذا مشروع لم يُراجَع أمنيًا خارجيًا.** تُنصح مراجعة مستقلة قبل أي إطلاق بيانات حقيقية، ونظام حماية البيانات الشخصية يحتاج استشارة قانونية.
